# Attachments and folders: v2026.09.26-13

Send a photo, document, audio clip or video in a private WhatsApp conversation with Carbon. It becomes a private immutable resource owned by the verified sender UUID. Forwarded files belong to the participant who uploads them. Filenames, captions and declared MIME types are untrusted metadata; they never become disk paths or permissions. View-once/disappearing messages and offline history are not imported. Carbon stores ordinary uploads without asking for permission.

The transport records a bounded media reference in SQLite before download. The worker downloads through the pinned WhatsApp library's streaming, authenticated decryption path, verifies the plaintext digest and length, and publishes the resource and ownership atomically in SQLite after durable Git/LFS writes. Failed or incomplete downloads are not published. The existing provider-message key deduplicates uploads. Pending downloads resume after restart; interrupted model work still requires operator reconciliation. Download references/keys are removed after storage, failure or unlink. No raw contents, filenames, captions or keys enter activity logs.

Files are materialized at `/data/content/resources/<resource UUID>/content.bin`; notes/folders retain their existing immutable representation. Blobs over 4 KiB use local Git LFS objects. SQLite stores resource kind, declared MIME, logical parent, ownership and grants. Logical moves do not rename physical files or change resource identity. All content, metadata, queues and credentials remain under the existing whole-`/data` backup boundary.

## What the model can do

`list_notes` now lists up to 100 authorized notes, files and folders, including kind, byte size, MIME and parent UUID. `read_note` accepts notes and UTF-8 text files up to 16 KiB with `text/plain`, `text/markdown`, `text/csv` or `application/json` MIME. Invalid UTF-8 and binary formats are rejected. `analyze_image(id, question)` can inspect JPEG, PNG and WebP using the selected model through the existing proxy. The proxy supports image content blocks, but model IDs do not advertise vision capabilities: select a vision-capable model. Unsupported-provider responses return a tool error. Provider PDF interpretation and audio transcription are described below. Video understanding and cross-recipient delivery remain future capabilities.

Image reads recheck recursive access, verify immutable Git/LFS bytes and length, and record source provenance before model submission. Byte signatures determine the MIME rather than the uploader's declaration; full decoding is delegated to the provider. At most two attempts are allowed per admitted request, each with one image up to 8 MiB, a 2,000-byte question, the existing 90-second proxy timeout and 1 MiB response cap. Analysis output is limited to 12,000 bytes and 800 requested tokens. Image bytes never enter ordinary conversation history or activity logs.

The analysis call contains only a fixed prompt, the question and the authorized image, without tools or unrelated conversation history. Responses containing tool calls are rejected. Image text and analysis are untrusted evidence, not authority. Permission-epoch changes invalidate in-flight results; derived notes retain source dependencies. This limits actions from image prompt injection but does not guarantee factual accuracy. No automatic cross-recipient delivery is introduced.

`create_folder` creates a private logical folder for the caller. To organize an existing resource, the model proposes `move_resource` with `resource` and `parent` (a folder UUID, or null for root). Only the same owner can move the resource into their folder. Moves require explicit approval from any configured admin, including the requester, even between private folders in this pilot. Cycles, excessive nesting, unauthorized ownership changes and stale proposals are rejected.

Read grants on a folder apply additively to descendants. Revoking a folder grant removes that inherited route; a remaining direct or other inherited grant can still allow access. A direct child grant does not expose a private parent's name or contents. Source-provenance checks apply independently to every requested resource. Folder sharing and moving into shared folders cannot widen access to a derived resource's restricted sources. Conservative provenance may require sharing sources first; no automatic declassification is introduced.

Creating private folders, uploading files and reading already-authorized resources need no review. Sharing folders/resources and moving them are administrative changes with 2PR. The existing global model-context/output invalidation barrier remains; scoped contexts are still planned.

## Provider-based document and audio understanding

`analyze_document(id, question)` sends an authorized PDF to the selected model through the proxy Files and Responses APIs. This includes scanned and mixed PDFs: there is no local PDF parser, text extractor, OCR engine or parser subprocess. `analyze_image` continues to send JPEG/PNG/WebP directly to the selected vision-capable model. `read_note` still reads authorized bounded UTF-8 text without format interpretation.

`transcribe_audio(id, question)` sends an authorized Ogg/Opus, WAV, MP3 or FLAC file to xAI's `/stt` endpoint using `grok-voice-transcribe-2.0`. Transcription is a separate provider model, not automatic routing by Grok's chat endpoint. The existing chat model selector stays unchanged. The transcript returns to the conversation model for reasoning. This does not interpret music or environmental sounds. Other containers and video understanding are unsupported; those uploads remain stored. Adding formats must use a verified provider path, not local conversion or OCR.

Carbon enforces ownership/source-aware ACLs, immutable-byte integrity, container signatures and the 8 MiB upload limit. It records source provenance and rechecks the authority epoch after asynchronous processing. Summaries inherit source restrictions. Ordinary authorized analysis needs no extra permission prompt. Provider requests are isolated from other conversation history, with no application tools enabled. Document instructions remain untrusted data. File search may be performed internally by the provider against the supplied document; Carbon does not enable web search or code execution.

PDF/audio tools share two attempts per conversation request; image analysis retains its own two-attempt limit. Questions are capped at 2,000 bytes, HTTP responses at 1 MiB and accepted interpretations at 12,000 bytes. Calls time out after 90 seconds; PDF output is limited to 1,600 tokens. Incomplete/error responses fail rather than being presented as a successful analysis. There is no locally enforced PDF page-count limit now: the model must state uncertainty, unreadable pages and incomplete coverage. A model answer is not proof of exhaustive review.

The initial PDF/audio adapter supports an **xAI-only Reefy proxy**. Multipart routing is not model-aware in the current proxy. Carbon checks that every reported model is xAI before sending bytes and refuses mixed/empty inventories; this inventory check is not atomic with external proxy reconfiguration. Keep provider configuration stable during requests. Explicit, request-bound provider routing and account binding are required before enabling these adapters on multi-provider devices. Image analysis still uses model-addressed JSON calls.

PDF uploads use generic filenames and an explicit one-hour provider expiry, followed by immediate deletion on success or failure. Responses use `store:false`. SQLite `/data/state/carbon.sqlite` records temporary file IDs and the proxy URL so cleanup can retry after restart, even without WhatsApp linked. Failed cleanup retries at most two files per minute, with ten-second deletion deadlines; expiry is the fallback for crashes, lost upload responses and prolonged outages. Cleanup never switches proxy URLs automatically. Provider/account changes during pending cleanup rely on expiry for the old account; old backups must not be used to replay analysis. No public document URL is created, and activity logs contain no document text, transcripts or provider IDs. Provider data-retention policy still applies separately from deleting uploaded Files objects.

API references: [xAI chat with files](https://docs.x.ai/developers/model-capabilities/files/chat-with-files), [file lifecycle](https://docs.x.ai/developers/files/managing-files), [speech to text](https://docs.x.ai/developers/model-capabilities/audio/speech-to-text).

## Sending files back

`send_file(id)` stages an accessible stored file or note for the current participant. Rust binds the actor and destination to the authenticated inbound message; the model cannot supply a phone number, recipient, filesystem path, URL or new caption. Read permission is sufficient; no new 2PR or routine confirmation is needed. This does not introduce cross-participant messaging.

Staged requests become pending atomically with successful completion of the model turn. A failed turn cancels its staged files; startup cancels unfinished staging. The unique inbox/resource pair prevents repeated tool calls from duplicating delivery. Carbon replies with text before dispatching the files. Files are uploaded with fresh encryption through the native WhatsApp library and delivered as document attachments; notes use Markdown, other files use an opaque MIME, and filenames are sanitized. Raw contents and encryption metadata never enter activity logs.

The worker checks source-aware access, the exact current identity binding and the permission epoch before upload and again before sending. It verifies immutable Git/LFS bytes before upload. Requests expire 24 hours after the inbound message. Unlink cancels outstanding delivery. Both upload and send have 45-second deadlines. A successful send means the transport accepted it, not that the recipient read it. Failed uploads are recorded as failed; send errors/timeouts and restart-interrupted sends become unknown and are never automatically replayed. Delivery results appear in activity logs; user-facing recovery/status tools are still planned.

Limits: three distinct resources per request, 20 files / 32 MiB per participant and 200 files / 256 MiB globally per rolling 24 hours. Failed and cancelled attempts remain counted. Each file retains the 8 MiB limit. The SQLite queue lives in `/data/state/carbon.sqlite` within the existing backup boundary; its migration preserves existing records.

## Fixed pilot limits

- 8 MiB per attachment, with a bounded streaming writer and a 45-second job timeout, plus a 30-second underlying HTTP timeout, bounded response size and disabled HTTP redirects.
- 32 MiB of admitted uploads per participant and 256 MiB globally per rolling 24 hours, counted before downloading and including failures.
- 128 MiB stored per participant, 1 GiB globally, and the existing 100-resource limit per participant (notes, files and folders combined).
- A maximum hierarchy depth of 16 resources, with bounded source traversal.

Admission failures are logged without file details; automatic user-facing admission-limit replies remain planned. Download/storage failures after admission receive a fixed reply. Malware scanning is not implemented: uploaded content is never executed; authorized attachments can be sent to the configured model provider for interpretation. Future parsers/download surfaces need their own resource and content-handling policy.

## Verification and upgrade

Regression tests cover ownership isolation, metadata/path abuse, size/budget enforcement, checksum failures, deduplication, restart recovery, Git/LFS bytes, unlink cancellation, opaque binary handling, folder inheritance, revocation, cycles, unauthorized moves and source-restricted derivatives. A mock-model E2E test starts with a stored upload, reads its text through the scoped tool, and verifies the reply goes only to its owner without another participant's data or download secrets in context. Container smoke checks verify the real deployment. Live provider media transfer has not been exercised with a real participant's attachment by these tests.

The migration adds metadata/queue tables and indexes; existing notes become root-level note resources with unchanged owners and grants. Pending read-grant proposals from older revisions can become stale and require resubmission. Do not downgrade an actively used volume to an image that lacks its resource/permission semantics. Restore only a complete consistent snapshot with transport disconnected until reviewed.

Image regression tests also cover cross-user denial, isolated model payloads, derived-note provenance, forged actors, MIME spoofing, LFS corruption, provider rejection, unexpected tool calls and authority changes during analysis. Provider-level vision quality and a real WhatsApp photo round trip require live validation.

Next: recipient-scoped work contexts and safe coordination delivery, additional provider-supported formats and cross-recipient file delivery. [Owner-only note editing and history](note-revisions.md) are implemented. Shared folder editing, attachment replacement, automatic shared-version updates, retention/compaction and protected reviewer recovery remain separate roadmap items.

File-reply tests cover model-supplied destination rejection, cross-tenant denial, duplicate calls, staged publication/cancellation, identity changes, access revocation before and after claiming, expiry, quotas, unlink and restart recovery. Tests exercise the mocked model through the durable dispatch boundary; real WhatsApp upload/delivery still requires live validation with a linked pilot account.
