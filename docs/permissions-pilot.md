# Permission pilot: v2026.09.26-08, extended in v2026.09.26-09

Carbon now supports immutable text notes shared with a participant UUID, a group UUID, or everyone admitted to this Carbon instance. Everyone includes future participants, not the public internet. SQLite remains the authority; Git/LFS stores content. Reviewers and group administrators receive no implicit access to private content.

## Current approval policy (v2026.09.26-17)

Any configured admin may approve any valid pending request, including their own. One admin is sufficient; the setup UI starts with one selector and supports adding/removing more before the initial set is sealed. Independent second-person review is no longer required. This policy applies to existing configured admins too. The LLM still cannot approve: Rust requires an exact request-bound human command, rechecks current requester/admin authority and rejects forwarded, stale, expired or replayed approvals. Admin status grants no implicit read access to private content. Initial enrollment is still one-time; subsequent admin additions/removals require the same human approval flow. Lost-all-admins recovery remains planned.

Participant and debug labels use `+phone (@lid)` when the native WhatsApp mapping is available. Missing mappings show `Phone unavailable (@lid)`; Carbon never treats LID digits as a telephone number. Labels are display metadata only, and do not merge participants, rebind identities or grant permissions.

## Using it

Select one or more distinct verified admins in the existing setup panel. Each must first send a private incoming message. Then ask Carbon through WhatsApp to create a group, add a known participant, or share an owned note. The model uses `permission_directory`, `propose_change` and `proposal_status`; it cannot apply or approve a change itself. Ordinary participants can propose sharing/revoking their own notes; group management requires administrative authority. Managers can enumerate verified participants; ordinary participants can discover only recipients within their enabled coordination scopes. Direct grants currently require a known UUID; richer recipient discovery remains future work.

Rust sends concise canonical notices, for example: “Create group **Community**? Reply to this message with **approve** or **reject**. Expires in 24h.” Use WhatsApp **Reply** on that notice. Commands are case-insensitive; `approving` and `rejecting` are also accepted. The quoted stanza ID and exact authenticated recipient must match the durable outbound notification mapping. The mapping is committed before network delivery; inbound quote metadata is stored atomically with inbox admission. A standalone approve, wrong-recipient quote, forwarded command or model tool call cannot authorize a change. Older explicit UUID commands remain accepted for compatibility but are no longer advertised. Approval works without a selected model and after ordinary request limits are exhausted for a sealed reviewer.

Summaries are frozen at proposal creation, generated by Rust and contain no raw JSON or long UUIDs. Private resource titles/content stay private; other target references use persisted numeric aliases that survive renames and SQLite VACUUM. Group names are bounded and stripped of control/WhatsApp formatting characters. The operator UI exposes approval metadata only, not resource bodies. Existing confirmed-delivered pending notices receive one replacement on upgrade; uncertain sends are never automatically replayed. Replacements retain the original expiry and state checks.

Requests expire after 24 hours. Rust revalidates the requester, reviewer and target revision inside the transaction that changes access, consumes the request, writes the audit and queues the result. Replay and stale changes cannot apply. Pending proposals survive restart; interrupted notification sends become unknown and are not retried automatically. Unlinking cancels pending requests and notifications. `pending_reviews` lists active requests visible to the requester or sealed reviewer, including exact operations and instructions for replying to the approval notice. Proposal status remains queryable by requester/reviewer; automatic expiry currently does not send a separate notification.

Supported operations: add/remove approval admin, create group, add/remove member, enable/disable group administration, grant/revoke read access. Members of an administrative group can manage ordinary groups. Only sealed reviewers can change administrative capabilities or privileged memberships. Every such mutation requires explicit approval from any configured admin, including the requester. Membership alone does not grant group-management authority. Planned handoff through reviewed admin additions/removals is implemented. Emergency recovery and self-service identity relinking are not.

## Revocation and provenance

Notes saved after reading/listing other notes conservatively inherit those source dependencies. A derived note can only be shared with an audience already authorized for every source; recursive checks prevent a copied summary from outliving revoked source access. Dependency traversal is bounded and fails closed. This may be stricter than necessary; there is no model-chosen declassification tool.

For this pilot, any approved access/group change invalidates all pending model replies and excludes earlier conversation history from future prompts. Stored history is retained, but a user may need to restate a request. Saved derived-note dependencies remain intact. This deliberately conservative global barrier will become scoped invalidation when generic work contexts and recipient-scoped coordination are implemented. It cannot retract messages already delivered.

Routine private conversations, reading already-authorized notes, and saving private notes do not request permission. 2PR applies to changes in authority. Folder inheritance and attachment storage were added in v2026.09.26-09; see [attachments and folders](attachments-folders.md). Owner-only note revisions and bounded pairwise coordination are implemented; shared-version publication remains planned. See [scoped coordination](scoped-coordination.md). Resource-enabled scopes are approved once; fresh non-forwarded uploads quoting the pair are admitted automatically with pair-local authority. Existing files still require both participants’ read access. No global file grant or per-upload review is created.

## Bounds and verification

Fixed pilot bounds: 200 groups, 20 proposals per requester per rolling 24 hours, 50 pending proposals globally. Repeating an identical pending proposal reuses its request ID. These supplement existing request/resource limits; configurable administrative budgets and broader control-lane abuse protection remain planned.

`cargo test --locked` covers pending access denial, verified admins, single-admin setup and explicit self-approval, exact commands, forwarding, expiry, replay, stale membership/capability changes, delegation limits, revocation of derived notes and queued replies, restart, group/everyone grants and a mock-LLM-to-approval-to-shared-read journey. `node tests/ui_state.cjs` checks collapsed defaults and QR loading transitions. The Linux container smoke test verifies deployment behavior. No test sends real review messages to participants.

## Rollback boundary

Do not run a pre-permissions image against this volume after shared or derived notes have been created: older code does not enforce source dependencies. Recovery to an older release requires a complete, consistent pre-upgrade data snapshot and review before reconnecting transport. A newer image must preserve these authorization checks.

## Approval-admin changes (v2026.09.26-20)

Initial web enrollment remains one-use. Existing approval admins can now propose adding/removing verified approval admins through WhatsApp, with the same human reply-bound approval flow and last-admin protection. A group admin cannot grant this role. This supersedes earlier statements that the configured reviewer set cannot change after setup. See [admin management](admin-management.md) for pending-request handoff, role generations, display identity and recovery limits.
